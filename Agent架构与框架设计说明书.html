一、项目背景与设计目标

本项目面向「AI 出图产品」的用户提供 7×24 小时智能客服，核心场景是产品功能咨询、常见问题解答与转人工。设计目标（按优先级）：

优先级目标说明
P0回答可控、可追溯客服场景对幻觉零容忍，答案必须来自知识库（RAG 引用下发），不允许 LLM 自由发挥
P0链路稳定、可降级任何外部依赖（LLM/Milvus/Redis/MinIO）故障都不能阻断主流程，必须有 mock/兜底路径
P1低延迟流式响应SSE 逐 token 下发，首字延迟 < 2s
P1小团队可维护2~3 人团队、无专职算法，架构必须简单直白、调试链路清晰
P2多渠道可扩展后续接入智齿/七鱼/Chatwoot 等第三方客服平台，渠道层可插拔

二、Agent 类型定位

结论 本项目是一个 RAG + 意图路由的单体客服 Agent（RAG-based Intent-Routed Single Agent），采用固定管道编排架构（Pipeline Orchestration）。ChatService 是唯一编排器，LLM 在管道中作为子任务执行器被串行调用 3 次，而非自主决策者。

2.1 在 Agent 能力光谱中的位置

能力维度本项目说明
Agent 数量单 AgentChatService 唯一编排器，无多 Agent 协作
推理模式确定性 if-else 管道非 ReAct 推理循环、非 Plan-and-Execute
工具调用（Tool-use）无LLM 调用不传 tools 参数，不自主调用函数
知识获取RAG（混合检索）向量 + 关键词双路召回，RRF 融合
记忆机制短期对话记忆Redis 滑动窗口（最近 10~20 条）+ MySQL 持久化
Agent 框架依赖无不依赖 LangChain Agent / AutoGen / CrewAI，纯自研编排
命名澄清 代码中的 "Agent" 字样（应用名「AI 出图产品智能客服 Agent」、模型名 ai-customer-agent）是产品命名，指"面向 Agent 化产品的客服系统"，不是框架级的自治 Agent 实体。这是一类业界常见的「Workflow 型 AI 应用」，Google A2A 语境下属于 Single-agent workflow。

2.2 为什么定位成"单体编排式"而不是"自治 Agent"

  • 场景收敛：客服 QA 是单一域任务，问题空间可枚举（产品咨询 / 闲聊 / 模糊），不需要跨域自主规划；
  • 可控性要求：固定管道每一步的行为可预测、可单测、可审计——客服回答出错的排查成本远高于灵活性收益；
  • 成本与延迟：ReAct 式自治 Agent 单轮需要 3~8 次 LLM 往返；固定管道把 LLM 调用压缩到精确的 3 次（意图/改写/生成），延迟和 token 成本降低 50% 以上；
  • 团队匹配：2~3 人全栈团队维护一套 if-else 管道的门槛，远低于维护自治 Agent 的 prompt 调优与行为回归测试。

五、框架选型论证：为什么自研轻量编排

5.1 候选框架对比

方案Agent 类型优势劣势（对本项目）结论
自研固定管道
（本项目采用）		 Workflow 型单 Agent 零框架依赖；行为 100% 可预测；每步可单测；延迟/成本精确可控；调试链路直白 流程变更需改代码（已用 SystemConfig 配置化缓解） ✔ 采用
LangChain / LangGraph Chain / Graph Agent 生态最全，RAG 组件丰富，上手快 抽象层厚、版本碎片化严重；SSE 流式需绕过其封装；深度定制（混合检索 RRF、双层意图）时反而要大量"打穿"框架；依赖树臃肿 ✘ 否决
AutoGen / CrewAI 多 Agent 协作 角色分工、任务委托能力强 本项目是单域任务，无多角色协作需求；多 Agent 通信使延迟×3~5、token 成本×3~5，且行为不可预测，违反 P0 可控性目标 ✘ 否决
ReAct 自治 Agent
（LLM 自主规划+工具调用）		 自治单 Agent 泛化能力强，能处理开放任务 客服 QA 问题空间可枚举，用不上自主规划；推理循环不可审计；幻觉风险高（违背 RAG 引用可控原则） ✘ 否决
Dify / Coze 等低代码平台 可视化 Workflow 零代码搭建、迭代快 私有化部署与深度定制受限；混合检索、双层意图、渠道适配等需求需写大量自定义插件，最终变成"平台里写代码" △ 备选

5.2 选型决策的四个核心论据

  1. 任务形态决定架构形态。Anthropic 在《Building Effective Agents》中的核心结论：能用固定工作流解决的，不要用自治 Agent。客服 QA 恰好是"输入可分类、步骤可枚举、输出可模板化"的典型固定工作流场景。
  2. 可控性 > 灵活性。客服回答直接面向终端用户，产品要求"答案必须有知识库出处（source 事件下发引用）"。固定管道保证每个回答都经过 RAG 检索；自治 Agent 则可能在推理循环中跳过检索、自由发挥。
  3. 性能与成本可预算。固定管道 = 恒定 3 次 LLM 调用，成本与延迟可精确估算；自治 Agent 的调用次数是运行时变量，无法做容量规划。对 QPS 可预期的客服入口，这一点是硬需求。
  4. 团队能力匹配。2~3 人团队维护自研管道只需 Python 工程能力；引入 LangChain 生态则需要持续跟踪其版本演进、抽象变更，隐性维护成本高于自研。
一句话论证 本项目的需求是"可控、可追溯、低延迟的单域客服 QA"，而固定管道单 Agent 是该需求下复杂度最低、可观测性最高、成本可预算的解；引入任何自治 Agent / 多 Agent 框架都会引入本项目用不上的灵活性，并付出可控性与延迟的代价。

七、架构权衡（Trade-off）分析

取舍点获得了什么牺牲了什么，如何缓解
固定管道 vs 自治推理行为可预测、可审计、3 次调用成本恒定无法处理管道外的长尾问题 → 用 ambiguous 澄清 + 转人工兜底承接
单 Agent vs 多 Agent无 Agent 间通信开销，延迟低、调试简单无法并行执行多视角分析 → 客服场景本身不需要
自研 vs LangChain 生态零框架债、SSE 原生、深度定制自由失去现成组件 → 自研成本约等于学习框架"打穿"成本，且 RAG 组件（约 8 步）自研复杂度可控
双层意图 vs 纯 LLM 意图高频 case 0ms 0 成本，LLM 只处理长尾正则需人工维护 → 通过线上 badcase 回流持续补充规则

八、演进路线：何时升级为多 Agent 架构

当前架构不是终点，而是符合当前阶段的最优解。以下信号出现时，按序演进：

阶段触发信号演进动作
现在单域客服 QA、2~3 人团队固定管道单 Agent（当前形态）
演进 1需要查订单、改工单、调 API 等动作类需求引入 Tool-use：在管道第 3 步后挂工具调用（仍非自治，工具白名单由意图决定）
演进 2扩展到售后/技术支持/营销等多域，各域知识库与话术差异大拆为路由 Agent + 域专家 Agent（Supervisor 模式），域内仍是固定管道
演进 3出现需要多步推理的复杂工单（如跨系统排查）局部引入 ReAct/Plan-and-Execute，仅用于工单子流程，客服问答主链路保持固定管道
演进原则 每次演进都由真实需求信号驱动，而非技术追新。主链路（用户直接感知的问答）始终保持固定管道以保证可控性；Agent 化只发生在用户不可见的后台子流程中。

九、总结

架构一句话 「AI 出图产品智能客服 Agent」采用 RAG + 意图路由的单体编排式 Agent 架构：ChatService 作为唯一编排器，以 9 步确定性管道串联「意图识别（规则+LLM 双层）→ 混合检索 RAG（8 步流水线）→ 记忆加载 → Prompt 组装 → SSE 流式生成 → 双写持久化」，LLM 作为子任务执行器被精确调用 3 次；以自研轻量编排替代 LangChain/AutoGen 等框架，换取行为可控、成本可预算、链路可审计三大客服硬指标，并通过降级优先、配置化驱动、渠道适配层保证生产级稳定性与可扩展性。
