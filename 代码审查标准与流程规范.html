🎯一、审查哲学与原则

代码审查不是找茬，是教学与成长。 每一条审查意见都应该让提交者和审查者双方都学到东西。

原则说明
对事不对人审查的是代码，不是写代码的人。用"这段逻辑"而非"你的代码"开头。
解释原因不要只说"改这个"，要说清楚为什么要改、不改会有什么后果。
建议而非命令用"考虑使用 X 因为 Y"代替"改成 X"。除非是阻断性问题。
优先级清晰每条意见必须标注 🔴 Blocker / 🟡 Suggestion / 💭 Nit。
表扬好代码发现巧妙实现要明确指出，正向反馈比批评更能驱动质量提升。
一轮完毕一次性给出完整反馈，不要挤牙膏式分多轮补充意见。
优先级定义：
  • 🔴 Blocker — 必须修复才能合并。安全漏洞、数据丢失风险、竞态条件、API 契约破坏、关键路径缺失错误处理。
  • 🟡 Suggestion — 建议修复但不阻断合并。输入校验缺失、命名模糊、性能问题、缺少测试。
  • 💭 Nit — 锦上添花。风格一致性、文档补充、替代方案探讨。
📋二、审查流程（6 步工作流）
1

提交前自检（开发者）

开发者提交 PR/MR 前，对照审查检查清单逐项自检。确认：无 lint 错误、无遗留 console.log/print 调试语句、无硬编码密钥/密码、关键路径有错误处理、新功能有对应测试。

2

提交 PR/MR（开发者）

PR 标题格式：[模块] 动词 + 描述（如 [chat-service] 修复 SSE 流式输出中断后记忆未持久化）。PR 描述须包含：变更摘要、影响范围、测试方式、关联 Issue。指定至少 1 名审查者。

3

自动化检查（CI Pipeline）

PR 提交后自动触发 CI：Ruff 检查（后端）→ ESLint + TypeScript 编译（前端）→ 单元测试 → 安全扫描（bandit / npm audit）。CI 不通过的 PR 不得进入人工审查。

4

人工审查（审查者，48 小时内）

审查者在 48 小时内完成审查。审查顺序：先看整体设计 → 再逐文件检查 → 最后看细节。按优先级从高到低给出意见，表扬好的实践。

5

修改与回复（开发者）

开发者逐条回复审查意见：已修复的 commit 引用、不采纳的理由说明。不采纳 🔴 Blocker 级意见必须有充分理由。

6

合并（审查者 Approve）

所有 🔴 Blocker 解决后，审查者 Approve 并合并。合并方式推荐 Squash Merge，保持主分支历史清晰。

时效要求：审查者在 48 小时内响应；开发者 72 小时内完成修改；超时未响应的 PR 由团队负责人介入协调。
🐍三、后端审查标准（Python / FastAPI）
3.1 安全性（Security）
级别 检查项 审查要点与示例
🔴 异常信息泄露 禁止将原始异常信息直接返回给客户端。本项目多处存在 f"处理失败: {e}" 模式，泄露内部结构。
正确做法：对客户端返回通用错误消息，详细信息仅记入日志。
🔴 SQL 注入 确认所有数据库查询使用 SQLAlchemy ORM 或参数化查询。禁止字符串拼接 SQL。检查 text() 调用是否绑定了参数。
🔴 硬编码凭据 禁止在代码中硬编码 API Key、数据库密码、JWT Secret。检查 settings.py 是否从环境变量读取。默认密码 admin/admin123 必须在首次启动强制修改。
🔴 认证与授权 所有 /api/ 路径（排除 /auth/login、/docs、/webhook/** 等）必须经过 AuthMiddleware。管理端接口 /admin/** 必须校验 is_admin 字段。
🔴 Prompt 注入 用户输入拼接进 LLM Prompt 前，必须用分隔符隔离。当前 SYSTEM_PROMPT 使用 {context} 占位符注入知识库内容，需确认 context 内容不会被用户操控来覆盖 system 指令。
🟡 输入校验 所有 API 端点必须有 Pydantic Schema 校验入参。检查 webhook_router.py 中 platform 参数是否做了白名单校验。
🟡 密钥管理 crypto.py 的 _derive_key() 使用 SHA256 派生 Fernet 密钥——可接受但非最佳实践。建议未来迁移到 scrypt 或 PBKDF2 做密钥派生。当前实现不阻断，但需记录为技术债。
3.2 正确性与健壮性（Correctness）
级别 检查项 审查要点
🔴 异步上下文安全 ChatService._persist_messages 使用独立 AsyncSessionLocal 防止主会话关闭——这是正确做法，需确保新增的 service 方法同样遵守此模式。禁止在 finally 块中使用请求级 DB session。
🔴 降级策略一致性 所有外部依赖（Redis/Milvus/MinIO/LLM）的降级逻辑必须：①捕获具体异常而非裸 except Exception；②降级后记录 WARN 日志；③降级行为对上层透明。LLMService._force_mock 是实例级变量，多并发请求下可能互相影响——需评估线程安全性。
🟡 Webhook 防重机制 _processed_messages 是内存 dict，多 worker 部署时失效。建议迁移到 Redis SETNX + TTL。当前单 worker 可用，但需在 PR 中注明此限制。
🟡 资源泄漏 检查 AsyncOpenAI 客户端是否在应用关闭时正确调用 close()。LLMService.close() 已实现但需确认 main.py 的 lifespan 中有调用。
🟡 错误处理粒度 webhook_router.py 中 f"消息解析失败: {e}" 直接返回给调用方，可能泄露内部异常类型。建议返回通用消息 + 内部日志。
3.3 性能（Performance）
级别 检查项 审查要点
🟡 N+1 查询 检查 RAG 检索、知识库列表等场景是否存在循环内执行 DB 查询。使用 selectinload 或批量查询替代。
🟡 Redis Pipeline 使用 RateLimitMiddleware 正确使用了 pipeline 批量操作——这是好的实践，新增的 Redis 操作也应遵循。
💭 Token 估算精度 LLMService.count_tokens 用 len(text)//4 粗略估算，中文场景偏差较大。可选：引入 tiktoken 精确计算。
3.4 可维护性（Maintainability）
级别 检查项 审查要点
🟡 类型注解 所有函数签名必须有参数和返回值类型注解。当前后端覆盖较好，但 _process_and_reply 的 adapter 参数缺少类型。
🟡 文档字符串 Service 层和复杂函数必须有 docstring 说明用途、参数、返回值。当前 ChatService 的 docstring 质量很高——以此为标准。
💭 常量提取 魔法数字（如 chunk_size = 6、[:5]、[-10:]）应提取为命名常量并注释含义。
💭 Mock 逻辑隔离 llm_service.py 中 mock 回复逻辑占 ~150 行，建议提取到独立 mock_data.py 模块，降低 service 文件复杂度。
⚡四、前端审查标准（Vue 3 / TypeScript）
4.1 类型安全
级别 检查项 审查要点
🔴 禁止 any 当前 sse.ts 中 body: any 和 dispatchEvent(evt: any, ...) 丢失了类型安全。必须定义具体接口替代 any。
🟡 API 响应泛型 request.ts 响应拦截器返回 data as unknown as AxiosResponse 类型断言——可接受但需确保调用方正确使用泛型 request.get<UserType>()。
🟡 Props 类型 所有组件 defineProps 必须使用 TypeScript 接口或 withDefaults，禁止运行时默认值对象。
4.2 安全性
级别 检查项 审查要点
🔴 XSS 防护 MarkdownRenderer 渲染 LLM 返回内容前必须经过 sanitize。确认 markdown-it 未开启 html: true，或使用 DOMPurify 过滤 HTML。
🟡 Token 存储 当前 JWT 存储在 localStorage——存在 XSS 窃取风险。这是常见取舍，可接受但需在文档中注明风险。理想方案是 HttpOnly Cookie，但需后端配合。
🟡 敏感信息 检查 .env.production 中的 VITE_API_BASE_URL 是否指向正确生产地址。Vite 环境变量以 VITE_ 前缀会打包进前端 bundle，不可放密钥。
4.3 性能与体验
级别 检查项 审查要点
🟡 路由懒加载 确认 router/index.ts 所有页面级组件使用 () => import() 懒加载，减小首屏 bundle。
🟡 SSE 连接管理 sse.ts 的 DONE_CLOSE_TIMEOUT_MS = 5000 兜底超时设计合理。检查用户切换会话时是否正确 abort 旧连接，防止连接泄漏。
💭 大组件拆分 ChannelManagement.vue（694 行）过大，建议拆分为子组件 + composable。
4.4 代码规范
级别 检查项 审查要点
🟡 Composition API 统一使用 <script setup lang="ts">，禁止 Options API 混用。
🟡 响应式解构 禁止直接解构 reactive 对象（丢失响应性），使用 toRefs 或改用 ref。
💭 import 排序 第三方库 → 框架 → 项目内部模块，按字母序排列。ESLnt 的 import/order 规则可自动处理。
✍️五、审查意见格式规范

每条审查意见必须包含：优先级标记 → 问题定位（文件+行号）→ 原因解释 → 改进建议（含代码示例）。

标准格式示例
🔴 Security: 异常信息泄露
chat_service.py:211 — yield make_error_event(f"处理失败: {e}")

原因：将原始 Python 异常对象直接拼接进返回给客户端的 SSE 事件，可能泄露内部模块名、数据库表结构、API 端点路径等敏感信息，为攻击者提供攻击面侦察线索。
建议：对客户端返回通用消息，详细信息仅记入日志。

# 正确做法
logger.exception("ChatService stream failed")
yield make_error_event("处理失败，请稍后重试")
✅ Good Pattern: 独立 Session 持久化
chat_service.py:248 — async with AsyncSessionLocal() as new_db:

点评：在 finally 块中使用独立 AsyncSession 执行双写，避免主会话提前关闭导致写入失败——这是一个非常专业的设计。注释也清楚地解释了原因。建议其他 Service 方法参照此模式。

6.4 CI/CD Pipeline（GitHub Actions 示例）

项目根目录创建 .github/workflows/ci.yml：

name: CI
on:
  pull_request:
    branches: [main, develop]

jobs:
  backend:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: ai-customer-backend } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.13' }
      - run: pip install -r requirements.txt
      - run: ruff check app/
      - run: ruff format --check app/
      - run: bandit -r app/ -ll
      # - run: pytest tests/ -v --cov=app  # 待建立测试套件后启用

  frontend:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: ai-customer-frontend } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm run type-check
      - run: npm run lint
      - run: npm run build

🔍八、本项目特定审查要点

基于代码审查结果，以下是本项目的重点关注项：

🔴 当前最高优先级

  • ⚠️初始化 Git 仓库 + .gitignore
  • ⚠️配置 Ruff（后端）+ ESLint/Prettier（前端）
  • ⚠️建立 tests/ 目录 + pytest 基础测试
  • ⚠️修复异常信息泄露（6 处 f"...: {e}" 模式）

🟡 中期改进

  • 📋Webhook 防重迁移到 Redis
  • 📋LLMService._force_mock 并发安全评估
  • 📋前端 any 类型替换为接口
  • 📋Markdown 渲染 XSS 防护审计

✅ 值得保持的优秀实践

  • ✅全异步架构 + 降级策略 — 所有外部依赖都有降级方案，保证无依赖时也能演示，这是生产级意识。
  • ✅独立 Session 持久化 — ChatService._persist_messages 用独立 AsyncSession 防止主会话关闭，专业的异步上下文管理。
  • ✅SSE 连接管理 — sse.ts 用 XHR + onprogress 规避 Chrome fetch 流的 ERR_ABORTED 问题，且有 5s 兜底超时。
  • ✅Redis Pipeline 限流 — RateLimitMiddleware 用 ZSet 滑动窗口 + Pipeline 批量操作，高效且正确。
  • ✅API Key 加密存储 — crypto.py 用 Fernet AES 加密 API Key，不在数据库明文存储。
  • ✅Docstring 质量 — ChatService 的方法文档清晰描述了 9 步流程，是全项目的文档标杆。
👥九、审查者轮值与责任
角色 职责 要求
主审查者 逐文件审查代码逻辑、安全、性能 熟悉该模块业务逻辑；48h 内完成；给出带优先级的完整意见
副审查者 补充主审查者遗漏；关注跨模块影响 可选；至少浏览 PR 描述和 diff 摘要
安全审查者 审查涉及认证、加密、外部输入的改动 PR 涉及 auth/crypto/webhook/LLM prompt 时必须指定
团队负责人 协调审查冲突；审批超时 PR 审查者与开发者意见不统一时做最终裁定
审查者轮值原则：避免同一人连续审查同一模块超过 2 周，促进知识交叉传播。新人提交的 PR 由资深成员审查；资深成员的 PR 互审。
