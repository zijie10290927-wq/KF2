问题陈述

我们的 B2B SaaS 产品的目标用户——产品团队、设计团队和远程团队——在日常协作中频繁遇到工具切换摩擦问题。他们在产品内管理任务和文档，但一旦需要可视化的头脑风暴、流程梳理或信息架构讨论，就必须跳出产品，切换到 Miro、FigJam 等独立白板工具。

这种切换带来三个层面的痛点：

  • 认知负担过重：Miro 和 FigJam 功能过于丰富（模板库、投票、计时器、视频通话、嵌入 iframe…），用户为了完成一次简单的便签讨论需要面对大量不相关的 UI 元素。"Miro 功能太多，我们只需要基础的便签和连线"。
  • 上下文断裂：白板讨论的结论无法直接关联到产品中已有的任务、文档和需求条目，用户需要在两个系统之间手动复制粘贴。"希望能直接链接到我们产品中的其他对象（任务、文档）"。
  • 协作成本高：邀请外部协作者需要额外注册/登录独立工具，降低了协作意愿和效率。用户需要实时协作能力，但并不需要视频/音频等重型实时通道。
⚠️ 不解决的成本

每次工具切换平均耗时 3-5 分钟（登录 + 找到目标画板 + 上下文重建）。以一个 10 人团队每周 3 次头脑风暴计算，每月浪费约 6-10 人时。更重要的是，跨工具的信息断裂导致讨论结论无法追踪回原始需求，形成决策黑箱。

目标与非目标

目标

#目标衡量方式类型
G1 降低协作工具切换频率：用户无需离开产品即可完成可视化协作，减少对 Miro/FigJam 的依赖 月活团队中白板功能使用率 ≥ 30% 用户目标
G2 深度使用而非浅尝辄止：白板会话不是"打开就关"，而是真正用于深度协作 白板会话平均时长 > 15 分钟 用户目标
G3 竞品替代效应：吸引从 Miro 等外部工具迁移的团队 从 Miro 迁移过来的团队占比 > 20% 业务目标
G4 产品粘性提升：白板成为产品内高频使用的核心模块，提升整体留存 使用白板的团队次月留存率比未使用团队高 ≥ 15% 业务目标
G5 对象关联闭环：白板内容与产品内任务/文档形成双向链接，实现"讨论→决策→执行"的信息流转 ≥ 40% 的白板包含至少 1 个产品对象链接 用户目标

非目标

#非目标排除理由
NG1 移动端原生支持 用户研究明确指出"移动端不重要，主要在桌面端用"。移动端白板的交互复杂度高，ROI 不匹配。可在 P2 阶段评估响应式适配。
NG2 视频/音频通话集成 用户明确表示"实时协作很重要，但不需要视频/音频"。视频通话涉及 WebRTC 基建和合规审查，超出 2 人团队 3 个月的工程容量。应聚焦于实时画布协作。
NG3 复杂图表工具集（UML、ER 图、流程图专业符号） 定位是"比 Miro 简单"，核心场景是便签头脑风暴和简单连线，不是专业的架构图或 BPMN 工具。
NG4 模板库 / 模板市场 模板是 Miro 的核心护城河，自建模板库需要内容运营和审核流程，不适合 MVP 阶段。可在 v2 引入用户自定义模板。
NG5 公开分享 / 嵌入式白板 白板数据涉及企业内部信息，公开分享引入权限管理和安全合规问题。MVP 聚焦于团队内协作，外部分享作为 v2 评估项。
NG6 白板 AI 助手（自动聚类、智能摘要） 虽是差异化方向，但依赖额外的 LLM 调用成本和模型集成工作，不适合 MVP。可作为 v2 的创新亮点。
📌 竞品定位

比 Miro 更简单——砍掉模板库、投票、计时器、视频通话等重型功能，只保留核心的便签 + 连线 + 实时协作。比 Google Jamboard 更丰富——支持产品对象链接、实时多人光标、画板组织与搜索、基础形状与文字框。我们的差异化在于与产品工作流的深度集成，而非功能数量。

产品团队

产品经理 / 产品负责人 · 使用白板进行需求梳理和优先级讨论
作为产品经理，我想要 在产品内直接创建一个白板画板来组织需求头脑风暴，以便 不需要切换到外部工具就能完成需求讨论并直接在产品内追踪结论。
作为产品经理，我想要 将白板上的便签直接关联到产品中的需求条目或任务，以便 讨论结论不会丢失，能追溯到具体的需求或执行项。
作为产品经理，我想要 邀请团队成员实时加入白板并看到每个人的光标位置，以便 在远程环境下也能像面对面一样高效协作讨论。
作为产品经理，我想要 用连线在便签之间建立"依赖""拆分""关联"等关系，以便 可视化需求之间的结构关系，帮助团队理解优先级和依赖链。
作为产品经理，我想要 将白板导出为图片并附在需求文档中，以便 为不在场的利益相关者提供讨论上下文，加速决策审批。
🎨

设计团队

设计师 / 设计 Lead · 使用白板进行信息架构和用户旅程梳理
作为设计师，我想要 用便签快速搭建信息架构树和用户旅程图，以便 在进入高保真设计前先对齐结构和流程，减少返工。
作为设计师，我想要 用不同颜色的便签区分用户类型、页面层级和交互节点，以便 在白板上一眼看出信息架构的层级和分类。
作为设计师，我想要 在白板上贴截图或设计稿并加批注连线，以便 在设计评审时直接在图上标注修改方向，省去在 Figma 和聊天工具间反复跳转。
作为设计师，我想要 无限画布上自由平移和缩放查看全局和细节，以便 在复杂的用户旅程中随时切换宏观和微观视角。
作为设计 Lead，我想要 将白板链接分享给产品经理和开发，无需额外注册即可查看，以便 降低跨职能评审的参与门槛。
🌐

远程团队

远程团队 Lead / 分布式团队成员 · 使用白板进行异步和同步协作
作为远程团队 Lead，我想要 创建一个长期存在的"团队空间"白板用于日常同步站会，以便 团队有一个固定的协作锚点，不用每次重新找工具和链接。
作为远程团队成员，我想要 在白板上看到其他协作者的实时光标和操作，以便 在异步和同步混合的工作模式下都能感知到团队的协作动态。
作为远程团队成员，我想要 在便签上 @提及同事来分配任务或征求意见，以便 在白板讨论中直接触发通知，而不需要切到聊天工具同步信息。
作为远程团队 Lead，我想要 给白板设置权限——团队内可编辑、外部只读，以便 在安全可控的前提下与外部客户或供应商协作。
作为远程团队成员，我想要 在不同白板之间搜索和快速跳转，以便 管理多个项目或迭代的白板，不会因为画板太多而找不到目标。
⚠️ 边界场景
  • 空状态：新建白板时应提供空白画布 + 3 秒新手引导气泡（"双击添加便签"），而非空白页面
  • 离线/断网：实时协作断连时需提示"连接中断"，本地操作缓存，重连后自动同步
  • 冲突处理：两人同时编辑同一便签文本时，采用 CRDT Last-Write-Wins，不做复杂合并
  • 大量元素：单画板超过 500 个元素时性能降级提示，超过 2000 个阻止新增并引导拆分

≥ 30%

技术考虑与依赖

架构概要

白板功能需与现有实时同步架构兼容。核心架构决策如下：

层面方案选型理由
画布渲染 HTML Canvas 2D + 自定义渲染引擎（非 SVG DOM 操作） 500+ 元素场景下 Canvas 性能远优于 SVG DOM 操作；自定义引擎可控制虚拟化渲染
实时同步 复用现有 WebSocket 实时同步管道 + CRDT（Yjs 或自研）做操作合并 约束条件明确要求"与现有实时同步架构兼容"；CRDT 解决多人同时编辑的冲突问题
数据模型 白板 = 元素数组（JSON），每个元素含 type/id/position/size/content/metadata。整板 JSON 存储为单文档。 单文档模型简化实时同步——每次操作广播 JSON Patch 而非全量。元素级 CRDT 合并
对象搜索 复用现有搜索 API，增加 type_filter=task|doc|requirement @提及功能依赖现有搜索能力，不自建索引
权限 复用团队 RBAC 模型，增加 whiteboard 资源类型 不自建权限体系，与产品现有权限一致

关键技术风险

#风险影响缓解方案
T1 Canvas 渲染在大量元素（500+）时的帧率下降 用户体验严重退化，可能放弃使用 视口虚拟化（只渲染可见区域元素）+ requestAnimationFrame 节流；超 500 元素时降级提示
T2 CRDT 实现复杂度和性能开销 同步延迟高、内存占用大 评估 Yjs（成熟开源 CRDT 库）vs 自研轻量方案；P0 先用 Last-Write-Wins，P1 引入 CRDT
T3 2 人团队 3 个月交付 MVP 的时间压力 功能范围无法按时完成 严格守住 P0 范围；P1 可延后到 Q3；每周同步进度，范围有风险立即砍 P1 保 P0
T4 @提及对象链接的数据一致性 被链接的任务/文档删除后白板出现死链 对象删除时发 webhook，白板标记死链但保留快照信息（标题+类型）
T5 导出图片的前端性能（大画布 toDataURL） 浏览器卡死或 OOM 限制导出元素数量；超大画布改为服务端渲染导出（P1 方案）

依赖关系

依赖项类型负责方说明
现有 WebSocket 同步管道 P0 阻塞 后端团队 需确认管道支持高频增量消息（>10 msg/s/连接）。如不支持需评估扩容方案。
搜索 API P0 阻塞 后端团队 @提及功能依赖。需增加 type_filter 参数和 debounce 友好的响应时间（<200ms）。
团队权限模型 P0 阻塞 后端团队 新增 whiteboard 资源类型。需确认 RBAC 扩展机制。
通知服务 P1 后端团队 R11 @提及通知依赖。MVP 可不含通知。
文件存储 P1 基础设施 R13 版本历史快照和 R10 服务端导出需文件存储。MVP 前端导出不需。

#状态问题需回答方
